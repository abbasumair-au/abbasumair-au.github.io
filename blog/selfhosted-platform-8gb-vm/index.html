A Production-Shaped Platform on One 8 GB VM

October 24, 2026 · by Umair Abbas · 9 min read

TL;DR

I wanted a lab that behaves like a real platform, on one 8 GB OVH VM. It now runs GitOps, a service mesh, a secrets manager, metrics and single sign-on, and it reconciles itself from Git. Getting there meant five failures, mostly about firewalls, network policy and memory.

  • Result: 15 Argo CD apps, 32 pods, Entra ID login for Grafana and Argo CD, nothing exposed to the internet.
  • Cost: memory sits near 90%. Every limit is a deliberate decision.
  • Biggest lesson: on a small node, the budget is the hard part, not the tooling.

I wanted to practise platform engineering end to end: GitOps, a service mesh, a secrets manager, metrics and single sign-on. I did not want a cloud bill, so everything runs on one VM with 8 GB of RAM. This post covers the architecture, the trade-offs I made, and the failures that taught me the most.

Every change went through a small pull request that I reviewed and merged. The repo ended up with 33 PRs, and that count is part of the story.

Architecture

A request travels a surprising number of hops: my browser, Tailscale, a NodePort, the Istio gateway, the ambient mesh, and finally the pod. Meanwhile Argo CD pulls desired state from GitHub, External Secrets pulls values from Vault, and Grafana and Argo CD send logins to Entra ID.

The stack

  • k3s with flannel, kube-proxy, Traefik and servicelb all switched off.
  • Cilium as CNI and kube-proxy replacement, with default-deny network policies.
  • Istio ambient (ztunnel, istio-cni, istiod) with Gateway API as ingress. No sidecars, which matters on 8 GB.
  • Argo CD in an app-of-apps layout. Everything else is installed from Git.
  • cert-manager with a self-signed CA for a wildcard certificate.
  • Vault (single node) plus External Secrets, so no secret ever lives in Git.
  • VictoriaMetrics + Grafana for metrics, and podinfo as a demo workload.
  • Microsoft Entra ID as the OIDC provider for Grafana and Argo CD.

Nothing is exposed to the internet. The Istio gateway listens on a NodePort and is reached over Tailscale. For hostnames I skipped DNS entirely: grafana.<tailnet-ip>.nip.io resolves to the tailnet address, so I get real hostnames, real TLS and zero registrar work.

Design decisions and trade-offs

Each choice below was made for the 8 GB budget first and for realism second. The last column is what I paid for it.

Everything is a pull request

The rules I set for the repo were simple: one branch and one PR per intent, under 400 lines, a body that explains the why and the rollback, requests and limits on every workload, and nothing secret in Git. Argo CD then reconciles main into the cluster.

That discipline paid off. When a change broke something, the fix was one reviewable diff, and the history reads like a log of lessons learned.

What broke, and what it taught me

1. The firewall was eating the CNI

Symptom
The node looked healthy, but pods could not reach anything.
Root cause
UFW dropped traffic on Cilium's interfaces, cilium_host and the lxc* devices.
Fix
Allow both explicitly.
sudo ufw allow in on cilium_host
sudo ufw allow in on lxc+

Lesson: when networking fails silently, check the host firewall before you blame the CNI.

2. A DNS rule that blackholed DNS

Symptom
External Secrets reported ClusterSecretStore InvalidProviderConfig with context deadline exceeded.
Root cause
The Vault login timed out because DNS queries were dropped. My baseline policy used Cilium's L7 DNS rules (rules.dns with a wildcard), and in namespaces outside the ambient mesh that path blackholed queries.
Fix
Plain L4 DNS egress. I proved it in a scratch namespace before touching the shared policies.
# before (simplified): L7 DNS inspection, queries were dropped
toPorts:
  - ports: [{port: "53", protocol: ANY}]
    rules: {dns: [{matchPattern: "*"}]}

# after: L4 only
egress:
  - toEndpoints:
      - matchLabels:
          io.kubernetes.pod.namespace: kube-system
          k8s-app: kube-dns
    toPorts:
      - ports:
          - {port: "53", protocol: ANY}

Lesson: test policy changes in a scratch namespace first. A wrong rule is much cheaper to find there.

3. Ambient mesh needs HBONE and probe SNAT

Symptom
podinfo returned 503 through the gateway while the pod itself was healthy.
Root cause
In ambient mode the gateway reaches workloads over HBONE on TCP 15008, which my default-deny policy blocked. Readiness probes also failed, because the kubelet probe arrives from the ztunnel SNAT address 169.254.7.127.
Fix
Allow 15008 from the gateway namespace and the SNAT address as an ingress source.
ingress:
  - fromEndpoints:
      - matchLabels:
          io.kubernetes.pod.namespace: istio-ingress
    toPorts:
      - ports:
          - {port: "9898",  protocol: TCP}   # podinfo
          - {port: "15008", protocol: TCP}   # HBONE
  - fromCIDR: ["169.254.7.127/32"]           # kubelet probes via ztunnel SNAT

Lesson: the route to an app has more hops than it looks like: Tailscale, NodePort, gateway, ztunnel, pod. Each hop needs a rule.

4. Death by OOMKill

Symptom
Pods restarting, then Grafana in CrashLoopBackOff and the UI returning 503.
Root cause
8 GB goes quickly when a control plane, a mesh and a metrics stack share a node. The kills came in this order: the Argo CD application controller, VictoriaMetrics vmsingle, vmagent, and finally Grafana, which is hungry while it loads its bundled dashboards.
Fix
Honest requests and limits everywhere, and dropping very high-cardinality kube-apiserver histograms at scrape time.
Last State:  Terminated
  Reason:    OOMKilled
  Exit Code: 137
# vmsingle scrape config: drop series I will never query
metricRelabelConfigs:
  - action: drop
    source_labels: [__name__]
    regex: apiserver_request_(slo_)?duration_seconds_bucket|apiserver_response_sizes_bucket|apiserver_watch_events_sizes_bucket

# grafana
resources:
  limits: {memory: 512Mi}   # was 256Mi

Lesson: dropping metrics you never query is the cheapest memory you will ever save. The funniest culprit was my own screenshot tooling: a headless Chrome was the biggest process on the box more than once, so it now gets killed after every run.

5. Vault is a manual step, on purpose

Vault runs as a single node with one key share, initialised and unsealed by hand. The init output stays on the host and never touches Git. External Secrets then pulls values into Kubernetes secrets through a ClusterSecretStore using Kubernetes auth.

The trade-off is that Vault needs unsealing after every reboot. For a lab I accept that; for production I would use auto-unseal.

Single sign-on with Entra ID

Grafana and Argo CD both log in through Entra ID using OIDC. The client secrets are created in Entra, stored in Vault, and delivered to the pods by External Secrets. They never appear in the repo.

The sharp edges were small but real:

  • Argo CD only resolves $secretname:key references from secrets that carry the label app.kubernetes.io/part-of: argocd. The ExternalSecret template has to add it.
  • Right after az ad app create, follow-up calls can fail because the new app has not replicated yet. Retry rather than assume a bug.
  • In a tenant that enforces MFA, a plain az login is not enough. Use --tenant with --use-device-code.
  • Argo CD's own values are applied by Helm, not by Git, so changing them means a helm upgrade on the node.
target:
  template:
    metadata:
      labels:
        app.kubernetes.io/part-of: argocd   # required for $secret:key lookups
data:
  - secretKey: client_secret
    remoteRef: {key: entra/argocd, property: client_secret}

Limits of this setup

This is a lab, and I would not run it as it stands for anything that matters:

  • No high availability. One node means one failure domain.
  • Vault is fragile on purpose. One key share, manual unseal, and no tested backup of the init material yet.
  • Memory is at the edge. A new workload means retuning limits elsewhere, and optional integrations such as Datadog are switched off for that reason.
  • Self-signed certificates. Browsers warn until the lab CA is trusted.
  • Entra ID login is configured but I have not yet completed an interactive sign-in end to end. The button, the secrets and the redirect settings are in place.

What I would tell my past self

On a small node, the platform is not the hard part. The hard part is the budget: every default-deny policy, every mesh hop and every memory limit is a decision you have to make on purpose.

  • Test network policy changes in a scratch namespace before they hit shared ones.
  • Set requests and limits from day one, then raise limits only when you see an OOMKill.
  • Drop metrics you will never query.
  • Keep secrets out of Git by design, not by discipline: Vault plus External Secrets made that automatic.
  • Small PRs turn debugging into documentation.

Next steps

  • Back up the Vault init material properly and move to auto-unseal.
  • Rotate the Entra client secrets before they expire in a year.
  • Delete the initial Argo CD admin secret once SSO is confirmed.
  • Bring the optional observability integrations back once the memory budget allows it.
